# LocalSonar

Run your Sonar quality gate on your machine **before** pushing, so the pipeline scan doesn't surprise you.

```
LocalSonar <mode> <sourcePath> [options]

LocalSonar SpecificSln "C:\src\MyApp\MyApp.sln"
LocalSonar SpecificSln "C:\src\MyApp"            (folder with exactly one .sln/.slnx)
```

It checks the same things as the company gate (defaults in `appsettings.json`):

| Condition | Default |
|---|---|
| Build succeeds | required |
| Blocker / Critical / Major issues | 0 |
| Duplicated lines (%) | ≤ 3.0 |

Exit code `0` = passed, `1` = gate failed, `2` = bad arguments, `3` = scan error (e.g. build failed), `4` = mode not implemented yet.
Reports (`report.html`, `report.json`, `build.log`) go to a `reports` folder next to the exe, so your repo stays clean.

---

## How it works

**Issues** — LocalSonar runs `dotnet build --no-incremental` on your solution with the
**SonarAnalyzer.CSharp** Roslyn analyzer injected. That is the same analyzer SonarScanner for .NET
runs in the pipeline. Nothing is written into your repo: the analyzer is added through an MSBuild
file passed on the command line (`MsBuild/LocalSonar.targets`). Each project writes a SARIF log,
which LocalSonar reads and maps to Sonar severities using your quality profile (`rules.json`).

Like SonarScanner, it:
- turns off warnings-as-errors for the scan, so findings are reported rather than breaking the build;
- skips test projects (they're test code in Sonar, with a different rule set);
- honours `#pragma warning disable` and `[SuppressMessage]`;
- ignores generated code (`obj/`, `*.g.cs`, `*.Designer.cs`, `<auto-generated>` files).

**Duplication** — LocalSonar tokenizes every non-test `.cs` file with Roslyn and finds copy-paste the
way Sonar's CPD does for C#: **at least 100 identical tokens spread over at least 10 lines**, in the
same file or across files. String/number literals are normalized, so two methods that differ only in
a message text still count. The percentage uses Sonar's formula: duplicated lines ÷ total lines.

## One-time setup

### 1. Build it

Open `LocalSonar.csproj` in Visual Studio and publish, or from cmd:

```bat
dotnet publish -c Release -o C:\Tools\LocalSonar
```

### 2. Export your quality profile → `rules.json` (important)

Without this, LocalSonar doesn't know which rules are Major/Critical in **your** profile and only the
default "Sonar way" rules run. It takes a minute:

1. In SonarQube, open **Quality Profiles** → your C# profile. Copy the `qualityprofile=` value from the URL (the profile key).
2. While logged in, open this in the browser (replace the host and key):
   ```
   https://<your-sonarqube>/api/rules/search?qprofile=<KEY>&activation=true&actives=true&f=name,severity,impacts&ps=500
   ```
3. Save the page as `rules.json` next to `LocalSonar.exe`. (If the response says `"total"` above 500, also save `&p=2` and merge the `rules` arrays, or use option B.)

**Option B — automatic download:** fill in `SonarQube.Url` and `SonarQube.QualityProfileKey` in
`appsettings.json`, then set a SonarQube user token in an environment variable (never in the file):

```bat
setx LOCALSONAR_TOKEN squ_xxxxxxxxxxxxxxxx
```

LocalSonar downloads the rules into `rules.json` when the file is missing
(or on every run if `RefreshRulesOnEachRun` is `true`).

LocalSonar also uses `rules.json` to **switch on** every rule your profile enables (including ones
that aren't in "Sonar way"), and to drop Sonar rules your profile has turned off.

### 3. Make the analyzer available

**Online (default):** the `SonarAnalyzer.CSharp` package is restored from NuGet during the scan.
On a locked-down machine, it needs to be available from your company feed (Artifactory/Azure
Artifacts). Set `Issues.SonarAnalyzerVersion` to an exact version if your feed doesn't allow floating
versions — ideally the same version your SonarQube server uses.

**Offline:** download the `SonarAnalyzer.CSharp` .nupkg once, rename it to `.zip`, extract it, and point
`Issues.SonarAnalyzerDirectory` at the `analyzers\dotnet\cs` folder inside. No NuGet access is
needed after that.

### 4. Mirror your pipeline's exclusions

If your pipeline sets `sonar.exclusions` or `sonar.cpd.exclusions`, copy the patterns into
`Issues.Exclusions` and `Duplication.Exclusions`. Globs are relative to the solution folder,
e.g. `**/Migrations/**`, `**/*.Designer.cs`, `src/Legacy/**`.

## Daily use

```bat
C:\Tools\LocalSonar\LocalSonar.exe SpecificSln "C:\src\MyApp\MyApp.sln"
```

or with the included helper (drop it in the repo root or on PATH):

```bat
scan.bat C:\src\MyApp\MyApp.sln
```

Options: `--skip-issues` (duplication only, takes seconds), `--skip-duplication`,
`--config <file>`, `--output <folder>`.

### Optional: block a push that would fail the gate

Git hooks run in Git's own shell, so this works without PowerShell. Save as `.git/hooks/pre-push`:

```sh
#!/bin/sh
"/c/Tools/LocalSonar/LocalSonar.exe" SpecificSln "$(git rev-parse --show-toplevel)/MyApp.sln" || {
  echo "LocalSonar quality gate failed - push aborted (use --no-verify to override)."
  exit 1
}
```

## How close is it to the server?

- **Issues:** same analyzer, so findings match closely when `rules.json` comes from your profile and
  `SonarAnalyzerVersion` matches the server. Rules that need the full SonarQube engine (a few
  cross-file/security taint rules) won't appear locally.
- **Duplication:** an estimate built on the same 100-token / 10-line rule. Expect it to be close but
  not identical; leave yourself a margin (e.g. aim for under 2.5%).
- **Leak period / new code:** the server gate usually judges *new code* only. `SpecificSln` checks
  *all* code, so it is stricter. The planned `Compare` mode will cover new code only.
- Running the scan does a full rebuild of your solution's `bin/obj`. Close Visual Studio's build
  or let it finish first.

## Project layout (and where to extend)

```
Program.cs / LocalSonarApp.cs     entry point, error handling, exit codes
Cli/CommandLineOptions.cs         argument 1 (mode) + argument 2 (source path) + --options
Modes/                            IScanMode: turns the source path into a ScanTarget
  SpecificSolutionMode.cs         implemented
  PlannedScanMode.cs              placeholder for SpecificFile / Compare / Full
  ScanModeRegistry.cs             register modes here
Core/ScanTarget.cs                what to scan (projects, files, optional FocusFiles / ChangedLines)
Core/ScanPipeline.cs              runs analyzers -> quality gate -> reports (mode-agnostic)
Analysis/Issues/                  Sonar analyzer injection, SARIF reader, quality-profile rules
Analysis/Duplication/             Roslyn tokenizer + CPD-style detector
QualityGate/                      gate conditions
Reporting/                        console, HTML, JSON writers
MsBuild/LocalSonar.targets        injected into the scanned build (never into your repo)
```

**Adding the planned modes** — each one only needs a class implementing `IScanMode` that returns a
`ScanTarget`; the build, rules, duplication, gate and reports are reused as-is.

| Mode | What its `ResolveTargetAsync` would do |
|---|---|
| `SpecificFile` | Find the `.sln` that owns the file; return the full solution with `FocusFiles = { file }`. The whole solution stays the duplication corpus, so copies elsewhere are still found. |
| `Compare` | Run `git diff --unified=0 <base>...HEAD`, parse the changed line numbers into `ChangedLines`. Base branch could come from an extra option (`--base develop`, already captured in `CommandLineOptions.Extra`). |
| `Full` | Find every `.sln`/`.slnx` under the folder and put them all in `BuildEntryPoints`. |

Then replace its `PlannedScanMode` line in `ScanModeRegistry.CreateDefault()`.

**Other extension points:** a new check (e.g. coverage via `dotnet test --collect`) implements
`IAnalyzer`; a new output (CSV, SARIF for Visual Studio's error list) implements `IReportWriter`.
Register either in `ScanPipeline.CreateDefault()`.
